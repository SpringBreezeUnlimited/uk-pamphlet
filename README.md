### 校内マップの更新（1.0.34）

`map.html` は、各階を斜めに描いたベクター案内図へ更新しました。全体・各階・管理棟と中庭・体育館を切り替え、教室や地図番号から催事の詳細を開けます。スマートフォンでは案内図を左右に動かせます。下の検索欄は選択中の階にかかわらず、全エリアの催事名・教室番号を検索します。

- 混雑色は既存の `crowd` データを読み取ります。30分以上経過・更新日時なし・通信未確認の情報は灰色にします。複数の催事が同じ場所にある場合、詳細で各催事の状態を確認できます。
- 校内全体図は `campus-map.svg` に描き直しました。正門・校舎・中庭・体育館の位置関係、右側の連絡通路、立入禁止区域を示す簡略図です。画面内で開閉でき、拡大表示と元の詳細図へのリンクもあります。
- 混雑色を淡くし、表示中の全催事が未更新・要確認の場合は、同じ表示を各教室に繰り返さず上部に説明をまとめます。各催事の詳細では前回の状態・更新時刻を引き続き確認できます。色の凡例と読み上げ用の状態も保持します。
- 図は簡略案内です。管理棟・校舎周辺は番号順の案内で、実際の配置や通路・立入禁止区域は「校内全体図」から従来の `map.png` を確認してください。
- 表示処理は `map.js`、見た目は `map.css`。`VERSION` を `1.0.34`、Service Worker のキャッシュを `v34` に更新しています。

2026年10月16日：ローカルで320・390・768・1280px幅、41地点の表示、詳細・検索・混雑色・通信障害時の予備表示を確認しました。実機のタッチ操作と、公開サイトへの反映は別途確認が必要です。

## 1. 全体の仕組みと必要なもの

### 何をどこに保存しているか

| システム | このパンフレットでの役割 | 担当者が操作する場所 |
|---|---|---|
| GitHub | HTML・画像・プログラム・予備データの保管、変更履歴の管理 | リポジトリ（ファイルの保管場所）の画面 |
| GitHub Pages | GitHub に置いたファイルを Web サイトとして公開 | リポジトリの Settings → Pages |
| Firebase Authentication | 管理者・係のメールアドレスとパスワードによるログイン | Firebase の Authentication |
| Cloud Firestore | 公開中の催事・写真、混雑状況、担当者の権限、更新履歴の保存 | Firebase の Firestore Database |
| パンフレットの管理画面 | 催事の編集、混雑状況の更新、係への担当割り当て | 公開サイトの `admin.html` / `crowd-admin.html` |

来場者が GitHub Pages のサイトを開くと、プログラムが Firebase から催事や混雑状況を読み取ります。担当者が管理画面で保存した情報は Firebase に入り、来場者向けページへ反映されます。

**「サイトのファイルを更新する作業」と「管理画面から催事を更新する作業」は保存先が異なります。** GitHub を更新しても Firebase のデータは移りません。Firebase に保存しても GitHub の `events.json` は書き換わりません。

この構成では Firebase Hosting・Cloud Storage・Realtime Database・Cloud Functions は使いません。写真は縮小後、催事データに含めて Firestore に保存しています。設定に `storageBucket` があっても、Storage の利用開始は不要です。Node.js・Firebase CLI のインストールやビルドも、通常の公開手順には必要ありません。

### 準備するもの

- インターネットにつながるパソコンとブラウザ。
- 引き継いだこのフォルダ一式。作業前に、元の状態を日付付きの別フォルダへコピーする。
- GitHub アカウントと、Firebase コンソールに入る Google アカウント。
- 管理者・係が使えるメールアドレスと、それぞれのログイン用パスワード。
- 確認用のスマートフォンなど、計2台の端末。
- 翌年度の催事一覧、ポスター、校内図、開催日時、挨拶文、体育館の予定。

### 混同しやすい3種類の権限

| 権限 | できること | 渡す相手 |
|---|---|---|
| GitHub の編集・管理権限 | ファイル更新、公開設定の変更 | 制作・システム担当 |
| Firebase プロジェクトの権限 | データベース設定、ログインアカウント作成、ルール変更 | 制作・システム担当、顧問など |
| サイト内の `admin` / `staff` | 催事編集・全体管理 / 担当催事の混雑更新 | 生徒会管理者 / 当日の係 |

サイトで `admin` にしても、Firebase コンソールや GitHub に入れるようにはなりません。通常の係にはサイト内の `staff` 権限だけを渡します。

## 2. 既存環境を引き継ぐか、新しく作るか

### このフォルダに記録されている2026年度の情報

| 項目 | 記録されている値 |
|---|---|
| 公開サイト | [2026年度の公開先として記録されているページ](https://kanato0708.github.io/uk-pamphlet/index.html) |
| GitHub | 所有者 `kanato0708`、リポジトリ名 `uk-pamphlet`（既存手順書の記録） |
| Firebase プロジェクト ID | `uk-pamphlet-digital`（`firebase-config.js` の設定） |

これは引き継ぎ時の照合用です。所有権・アクセス権・稼働状態は前任者と確認してください。旧資料 [混雑状況_導入手順.md](混雑状況_導入手順.md) の「未実施」などの記述は作成時点の記録です。現在の作業順は本 README を使ってください。

### A. 同じ公開 URL・Firebase を使い続ける場合

1. 前任者から GitHub の編集権限と、公開設定を管理できる体制を引き継ぐ。
2. Firebase プロジェクトへのアクセス権を、後任の Google アカウントへ付けてもらう。
3. 後任自身のサイト用ログインアカウントを作り、`admin` 権限を付けてもらう。
4. [11章](#guide-11)のバックアップを取り、既存データを保管する。
5. [4章](#guide-4)・[5章](#guide-5)で設定を照合する。設定済みのプロジェクトやデータベースを作り直す必要はない。
6. [8章](#guide-8)で翌年度の内容に変更し、[9章](#guide-9)の確認を行う。

この場合、通常は `firebase-config.js` の変更は不要です。管理画面での変更は現在の公開サイトにも反映されます。昨年度版をそのまま残したい場合には向きません。

### B. 新しい GitHub・Firebase で作る場合

[3章](#guide-3)から順番に進めます。旧年度を残しながら準備する場合にも使えます。新しい URL になるので、QRコードや案内リンクも更新します。

**GitHub だけをコピーしても、Firebase は旧プロジェクトにつながったままです。** 新年度用に分ける場合は、新しい Firebase を作り、`firebase-config.js` を必ず新しい値に置き換えます。接続先を確認するまで、コピー先の管理画面から更新しないでください。

## 3. GitHub にファイルの置き場を作る

1. [GitHub](https://github.com/) に登録・ログインし、メールアドレスの確認を済ませる。
2. 右上の「＋」→ **New repository** を開く。
3. **Owner** に運用するアカウントまたは学校で管理する Organization を選ぶ。
4. **Repository name** に名前を入れる。例：`uk-pamphlet-2027`。半角英数字とハイフンにすると扱いやすい。
5. 無料の GitHub Pages を使う場合は **Public** を選ぶ。ファイルは誰でも閲覧できる。
6. **Add README** を有効にして作成する。仮の README は後でこのファイルに置き換える。
7. **Create repository** を押す。通常は `main` というブランチ（公開に使うファイルのまとまり）ができる。

ここでは保管場所を作るところまでです。Firebase の接続先を設定してから、[6章](#guide-6)でファイルをアップロードします。

GitHub Free の Pages は公開リポジトリで利用できます。学校の Organization を使う場合は、学校側で Pages の利用が許可されているかも確認します。[公式：GitHub Pages サイトの作成](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)

## 4. Firebase を一から設定する

### 4-1. プロジェクトを作成する

1. [Firebase コンソール](https://console.firebase.google.com/) を、運用に使う Google アカウントで開く。
2. 「プロジェクトを作成」または「プロジェクトを追加」を選ぶ。
3. プロジェクト名を入れる。例：`宇工祭2027デジタルパンフレット`。
4. プロジェクト ID を確認して記録する。例：`uk-pamphlet-2027-xxxxx`。ID は世界全体で重複できず、作成後は変更できない。
5. Google Analytics や AI 支援を尋ねられた場合、このパンフレットを動かすための有効化は不要。
6. 作成が完了したらプロジェクトを開く。最初は無料の **Spark** プランで設定・動作確認を進められる。本番利用量は[10章](#guide-10)で判断する。

### 4-2. Web アプリを登録する

1. プロジェクトの概要で **Web のアイコン `</>`** を選ぶ。すでに別のアプリがある場合は「アプリを追加」を使う。
2. アプリのニックネームを入れる。例：`宇工祭パンフレットWeb`。
3. Firebase Hosting の設定が表示されても選択せず、「アプリを登録」を押す。
4. Firebase SDK の設定情報を表示する。後からは、歯車 →「プロジェクトの設定」→「全般」→「マイアプリ」→ 登録した Web アプリ →「SDK の設定と構成」の **構成（Config）** で確認できる。
5. 手元の `firebase-config.js` をテキストエディターで開き、値を新しいプロジェクトの設定に置き換える。

ファイルの形は次のとおりです。`ここに…` の部分は説明用なので、実際の値に置き換えてください。Firebase が表示した値をそのまま使い、ドメインやバケット名を推測して作らないでください。

```js
export const firebaseConfig = {
  apiKey: "ここに apiKey",
  authDomain: "ここに authDomain",
  projectId: "ここに projectId",
  storageBucket: "ここに storageBucket",
  messagingSenderId: "ここに messagingSenderId",
  appId: "ここに appId",
};
```

先頭の **`export` を残す**ことが重要です。表示された設定のうちオブジェクトの値を移し、`<script>` タグ・`initializeApp`・追加の `import` はこのファイルに貼り付けません。現在のプログラムに初期化処理が入っています。

この Web アプリ用設定はブラウザへ配信するためのものです。アクセス権は後述の Firestore ルールで制御します。管理者のパスワードやサービスアカウントの秘密鍵 JSON は、設定ファイルや GitHub に入れません。

[公式：Web アプリへの Firebase の追加](https://firebase.google.com/docs/web/setup)

### 4-3. Cloud Firestore を作成する

1. Firebase のメニューで **構築（Build）→ Firestore Database** を開く。
2. 「データベースの作成」を押す。
3. エディションの選択がある場合は **Standard** を選ぶ。このプログラムは通常の Firestore 用。
4. データベース ID は **`(default)`** を使う。別名のデータベースは現在のプログラムの接続先にならない。
5. ロケーションを選ぶ。国内開催なら選択肢にある東京 `asia-northeast1` などを検討し、選んだ値を記録する。作成後の場所変更はできないので、確認して進める。[公式：Firestore のロケーション](https://firebase.google.com/docs/firestore/locations)
6. セキュリティルールの初期モードは **本番環境モード（Production mode）** を選ぶ。
7. 作成を完了する。この時点では一般のブラウザからの読み書きが拒否されるため、次の設定を続ける。

「Realtime Database」は別のサービスです。間違えて作った場合も、このプログラム用には **Firestore Database** の作成が必要です。[公式：Firestore の開始手順](https://firebase.google.com/docs/firestore/quickstart)

### 4-4. 権限ルールを公開する

1. Firestore Database の **ルール（Rules）** を開く。
2. このフォルダの [firestore.rules](firestore.rules) をテキストエディターで開き、全文をコピーする。
3. コンソール内のルールを全文置き換え、「公開（Publish）」を押す。
4. エラーなく公開できたことを確認する。

既存プロジェクトの場合は、現在のルールを別ファイルに控えてから比較します。ほかの学校システムも同じプロジェクトを使っているなら、単純な全文置換は避け、別のプロジェクトを使うか管理担当者と統合してください。

**`firestore.rules` を GitHub に置くだけでは、Firebase のルールは変わりません。** ファイルを更新したときも、この画面での公開が必要です。動かないからといって `allow read, write: if true;` にしないでください。

現在のルールは次の役割です。

- 来場者：公開催事・写真・混雑状況を読む。ログイン不要。
- 係：有効なアカウントで、割り当てられた催事の混雑状況を更新する。
- 管理者：催事の公開・編集、全催事の混雑更新、係の権限設定、履歴閲覧をする。
- 混雑状況の更新には、更新者と日時の履歴を同時に保存する。
- 係の情報や履歴を来場者全員に公開しない。

### 4-5. メール・パスワードのログインを有効にする

1. **構築（Build）→ Authentication** を開き、初回は「始める」を押す。
2. **ログイン方法（Sign-in method）** を開く。
3. **メール／パスワード（Email/Password）** を選び、メール・パスワードのログインを有効にして保存する。
4. パスワードなしの「メールリンク」は、このプログラムでは使わない。

このサイトのログインは Google ログインではありません。Firebase に入る Google アカウントと、サイト用のメール・パスワードは別のものとして登録します。[公式：メール・パスワード認証](https://firebase.google.com/docs/auth/web/password-auth)

### 4-6. 公開ドメインを登録する

Authentication → **設定（Settings）→ 承認済みドメイン（Authorized domains）** で、公開先のドメインを追加します。

例：公開 URL が `https://example-school.github.io/uk-pamphlet-2027/` なら、登録するのは **`example-school.github.io`** だけです。`https://` や `/uk-pamphlet-2027/` は含めません。独自ドメインを使う場合はそのドメインを登録します。

承認済みドメインはメールリンクやリダイレクトなどの認証処理に関わる設定で、Firestore の読み書きを制限するものではありません。このプログラムはメール・パスワード認証を使うため、まず4-5の有効化とユーザー登録を確認してください。公開先を変えても、`firebase-config.js` の `authDomain` は Firebase が示した値のままにします。[公式：認証のドメイン設定に関する説明](https://firebase.google.com/docs/auth/web/email-link-auth)

## 5. 最初の管理者を登録する

管理者の準備は **①ログインアカウントを作る → ②管理者権限を付ける** の2段階です。

### 5-1. Authentication にユーザーを作る

1. Firebase の **Authentication → ユーザー（Users）→ ユーザーを追加** を開く。
2. 管理者本人が利用できるメールアドレスとパスワードを登録する。
3. 作成したユーザーの **UID** をコピーする。

UID は Firebase が付ける識別番号です。メールアドレスや、自分で決めた表示名とは異なります。

### 5-2. Firestore に管理者の情報を作る

1. **Firestore Database → データ（Data）→ コレクションを開始** を開く。
2. コレクション ID に **`users`** と入力する。すでにある場合はそれを開いてドキュメントを追加する。
3. ドキュメント ID に、5-1でコピーした **UID をそのまま貼り付ける**。「自動 ID」は使わない。
4. 次の4フィールドを設定して保存する。

| フィールド | 選ぶ型 | 入れる値 |
|---|---|---|
| `displayName` | string（文字列） | 例：宇工祭2027管理者 |
| `role` | string（文字列） | `admin` |
| `active` | boolean（真偽値） | `true` |
| `eventIds` | array（配列） | 要素なしの空配列 |

`active` を文字列の `"true"` にしないでください。`eventIds` も、文字列の `"[]"` ではなく「配列」を選び、要素を入れずに保存します。

最初の管理者だけは Firebase コンソールから作ります。サイトのルールが「管理者だけが権限を設定できる」ためです。2人目以降のサイト内権限は[7章](#guide-7)の管理画面で設定できます。

## 6. GitHub Pages で公開する

### 6-1. ファイルをアップロードする

1. [3章](#guide-3)で作ったリポジトリの **Code** タブを開く。
2. **Add file → Upload files** を選ぶ。
3. このフォルダから公開用ファイルを選び、画面へドラッグする。初回は[13章](#guide-13)のファイルを一式そろえる。
4. **リポジトリの一番上に `index.html` がある形**にする。親フォルダごと入れたり、ZIP のまま置いたりしない。
5. 保存内容の説明を入れる。例：「2027年度パンフレットの初期設定」。
6. **Commit changes** で `main` に保存する。

このフォルダにある `.git`、`.DS_Store`、`tmp/`、`output/`、`monitor-display-update.zip` はサイトの動作には不要です。作業途中の資料や個人情報をまとめて公開しないよう、公開用ファイルを選んでください。`README.md` と `firestore.rules` は引き継ぎ資料として保管できます。

すでに同名ファイルがある場合は、そのファイル全体を置き換えます。特に `saiji.html` の内容を古い HTML の末尾へ追加すると、画面やボタンが二重になります。

### 6-2. Pages を有効にする

1. リポジトリの **Settings → Pages** を開く。
2. **Build and deployment → Source** で **Deploy from a branch** を選ぶ。
3. **Branch** を `main`、フォルダを **`/ (root)`** にして **Save** を押す。ブランチ名が違う場合はファイルを保存したブランチを選ぶ。
4. **Actions** タブで Pages の公開処理が成功するのを待つ。
5. Settings → Pages に戻り、表示された **Visit site** を開く。更新には数分から最大10分程度かかることがある。
6. HTTPS で開けることを確認する。**Enforce HTTPS** が操作できる場合は有効にする。

この構成では自分で GitHub Actions の設定ファイルを書く必要はありません。[公式：Pages の公開元設定](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

### 6-3. 使う URL を控える

公開先が `https://example-school.github.io/uk-pamphlet-2027/` の場合：

| 用途 | 公開 URL の末尾に付けるもの |
|---|---|
| 来場者向け表紙・QRコードの行き先 | `index.html` |
| 催事一覧 | `saiji.html` |
| 校内マップ | `map.html` |
| 生徒会管理者のログイン | `admin.html` |
| 催事編集 | `editor.html`（管理者ログインが必要） |
| 係・管理者の混雑更新 | `crowd-admin.html` |
| 校内モニター用表示 | `monitor.html` |

係には `crowd-admin.html` を案内します。`admin.html` は管理者専用なので、係としては入れません。来場者向けの QRコードは公開サイトの URL から作り、印刷前にスマートフォンで読み取って確認します。GitHub のファイル一覧の URL を使わないでください。

<a id="guide-7"></a>
## 7. 催事の初回公開と係の登録

### 7-1. 初回の催事データを公開する

1. 公開サイトの表紙にある **「生徒会役員の方はこちら」**、または `admin.html` を開く。
2. [5章](#guide-5)で作った管理者のメール・パスワードでログインする。
3. **「催事を編集」** を開く。
4. 新しい Firebase にまだ公開データがなければ、GitHub に置いた `events.json` が初回用として表示される。
5. 催事名・カテゴリ・場所・時間・説明・写真を確認し、**「更新して公開」** を押す。
6. **「公開が完了しました」** と表示されたら、別の端末で `saiji.html` と `map.html` を開いて確認する。

保存すると Firestore の `siteContent/events` と `publishedEvents` が作成されます。これらは手作業で空のデータを作らず、サイトから保存してください。

写真は「写真を選ぶ」から指定します。自動で縮小されますが、一度に写真を大量に追加して保存できない場合は、数件ずつ公開してください。「公開中のデータを再読み込み」は未保存の変更を破棄する操作です。

### 7-2. 混雑状況の対象を登録する

1. 管理者として `crowd-admin.html` を開く。
2. **「未登録の催事を登録」** を押す。
3. 「○件の催事を確認しました」と表示されることを確認する。
4. 新しく登録した催事は「未更新」になる。

2026年度の同梱 `events.json` は42件で、名前が「（なし）」の1件を除く41件が混雑更新の対象です。翌年度は編集後の件数で判断してください。このボタンは既存の混雑状況を初期化しません。前年のデータを使い続ける場合は、開催前に全対象を実際の状態へ更新します。

### 7-3. 係のアカウントと担当を設定する

1. Firebase の **Authentication → ユーザーを追加** で係のアカウントを作る。
2. そのユーザーの **UID** をコピーする。
3. サイトの `crowd-admin.html` に管理者として入り、**「係の権限・担当を設定」** を開く。
4. UID と表示名を入力する。表示名は例として「301教室担当」など、運用時に識別できるものにする。
5. 権限で **「係（担当催事のみ）」** を選ぶ。
6. **「更新権限を有効にする」** にチェックする。
7. 担当する催事を1つ以上選び、**「権限を保存」** を押す。
8. 係本人へ管理画面の URL とログイン情報を個別に伝え、本人の端末で確認する。

Authentication への登録だけでは更新できません。サイトの権限設定だけでもログインアカウントは作られません。必ず両方の作業を行います。

2人目の管理者も同じ手順で作り、手順5で **「管理者（全催事・権限設定）」** を選びます。担当欄にかかわらず全催事を管理できるので、運営責任者に限って付与します。

権限を止めるときは「登録済みの係・管理者」→「担当・権限を編集」→「更新権限を有効にする」のチェックを外して保存します。自分自身の管理者権限はこの画面から止められないため、別の管理者が作業してください。

<a id="guide-8"></a>
## 8. 翌年度の内容に変更する

### 8-1. 変更する場所を選ぶ

| 変えたいもの | 作業する場所 | 反映の方法 |
|---|---|---|
| 催事名・カテゴリ・場所・時間・説明・写真 | サイトの催事編集画面 | 「更新して公開」 |
| 混雑状況 | `crowd-admin.html` | 各催事の状態ボタン |
| 係の担当・有効／無効 | `crowd-admin.html` | 「権限を保存」 |
| 表紙、お願い、挨拶、体育館の詳細予定 | 対応する HTML ファイル | GitHub に同名でアップロード |
| 年度・テーマ・ページタイトル | 各 HTML、`manifest.json` | GitHub にアップロード |
| ポスター・地図画像・アイコン | 対応する画像ファイル | GitHub にアップロードしキャッシュも更新 |
| 地図の番号と催事の対応、ボタン位置 | `map-links.json`、`map-positions.json` | GitHub にアップロード |
| 接続する Firebase | `firebase-config.js` | GitHub にアップロード |
| データのアクセス権限 | `firestore.rules` | Firebase のルール画面で公開 |
| 通信障害時の予備データ | `events.json`、`map-local-data.js` | 公開中のデータから更新し GitHub にアップロード |

催事を一度 Firestore に公開した後は、**`events.json` だけを書き換えても、通常表示される公開催事は変わりません。** 公開内容は編集画面から変更し、予備ファイルは[付録](#backup)の手順で合わせます。

### 8-2. 年度・固定の案内・画像

1. `index.html`、`aisatsu.html`、`saiji.html`、`map.html`、`taiikukan.html`、`monitor.html`、`crowd-admin.html` などを確認する。
2. テキストエディターのフォルダ内検索で `2026` や前年のテーマを探し、画面に出る年度・タイトル・文章を更新する。
3. `aisatsu.html` の役職・氏名・挨拶文と、`taiikukan.html` のステージ名・時間を今年度のものにする。これらは催事編集画面とは別の固定ページ。
4. `manifest.json` の `name`・`short_name`・`description` も変更する。ホーム画面に追加したときの名称に使われる。
5. `poster.jpg` を今年度のポスターに、必要なら `map.png` やアイコンも同名で置き換える。拡張子を変える場合は参照元も修正する必要がある。
6. 画像を変更したら、`sw.js` 冒頭の `CACHE_NAME` も未使用の値にする。例：`ukousai2026-v19-2027-content`。

`CACHE_NAME` の先頭 `ukousai2026-` は、現在のプログラムが古いキャッシュを見分けるためにも使っています。表示上の年度ではないので、その先頭を残して後ろの版番号を変える方法が簡単です。フォルダ全体の `2026` を無差別に置換しないでください。

画像は端末のキャッシュ（表示を速くするための保存データ）に残るため、ファイルだけを置き換えると古い絵が出る場合があります。公開完了後、再読み込みとタブの開き直しで確認します。

### 8-3. 催事 ID と地図

催事には `1f-01` などの **`id`** があります。名前ではなくこの ID で、混雑状況・担当権限・地図が結び付いています。

- 同じ催事の名前や時間を直すときは、元の催事を編集する。画面編集なら ID は維持される。
- 新しい催事を追加すると、ID は自動で作られる。公開後に「未登録の催事を登録」と担当割り当てを行う。
- 削除して作り直すと別の ID になる。地図の対応は自動では変わらない。
- 前年の催事を今年度用に書き換えて同じ ID を使う場合、前年の混雑情報・係の担当が残る。古い係を停止し、担当と混雑情報を見直す。
- 催事を削除しても、地図の対応・古い担当設定・混雑履歴は自動削除されない。

新しい ID は Firebase の Firestore Database → データ → `publishedEvents` で、各ドキュメントの `name` と `id` を照合して確認できます。[付録](#backup)で保存する `events.json` でも確認できます。

`map-links.json` は「地図番号 → 催事 ID」の対応です。次はファイルの一部分の例です。

```json
{
  "1": ["1f-01"],
  "33": ["courtyard-04", "courtyard-05"],
  "gymA": ["gymA-01"]
}
```

実ファイルのほかの番号は残して編集します。同じ場所に複数の催事があるときは配列に複数入れ、催事がない番号は `[]` にします。現在の地図は **1～39・`gymA`・`gymB`** のキーを使うので、キー自体を消さないでください。40番以降を増やす場合は JSON の追加だけでなく `map.html` の変更も必要です。

`map-positions.json` の `x` は左から、`y` は上からの位置を0～100の百分率で指定します。例えば `x: 50, y: 50` は画像の中央です。地図画像を入れ替えた場合は、番号が正しい部屋に重なるか全体を確認します。

`map-local-data.js` は地図の予備データです。JSON や催事の変更は自動で複製されないので、変更後は[付録](#backup)で更新します。HTML のダブルクリックによる `file://` 表示だけで動作確認を終えず、公開 URL でも確かめてください。

## 9. 公開前の動作確認と当日の運用

### 公開前チェック

- [ ] 接続先 `projectId` が運用する Firebase と一致している。
- [ ] 来場者用 URL が HTTPS で開き、表紙・挨拶・催事・体育館・地図へ移動できる。
- [ ] 年度、開催日時、名前、会場、写真、テーマが今年度の内容になっている。
- [ ] 管理者がログインし、催事を1か所変更して公開できる。別端末で反映を確認し、試験用の記述は戻す。
- [ ] 管理者が全催事を登録し、今年度の係に担当を割り当てた。
- [ ] 端末Aで係として混雑状況を更新し、ログインしていない端末Bの `saiji.html` に反映される。
- [ ] 係には担当外の更新ボタンや管理者用機能が出ず、担当の催事だけ更新できる。
- [ ] 管理者で試験用の係を停止すると、その係が更新できなくなる。必要な係は試験後に戻す。
- [ ] 管理者画面の履歴に、更新日時・催事・状態・更新者が残る。
- [ ] 端末の通信を切ると、混雑状況が最新でない旨を表示する。再接続後も確認する。
- [ ] 地図の各番号から正しい催事が開く。追加・削除した催事も確認した。
- [ ] `monitor.html` を実際に設置する画面で表示し、文字サイズ・全画面表示・通信を確認した。
- [ ] 予備データとバックアップを更新し、利用量と料金プランを確認した。
- [ ] 印刷した QRコードを読み、正しい公開 URL が開くことを確認した。

同じブラウザのタブだけではログイン状態が共有される場合があります。管理者・係・来場者の確認は、別端末や別ブラウザのプロファイルを使うと確実です。

### 当日の係の操作

1. `crowd-admin.html` へログインする。
2. 担当催事を見つけ、実際の会場に合う状態を押す。
3. 更新完了の表示を確認する。通信失敗の場合は、接続が戻ってから押し直す。
4. 変化がなくても、運営で決めた間隔（例：5～10分）で現場を確認して同じ状態を押す。
5. 終了・受付停止時は「受付停止・終了」にし、作業後はログアウトする。

混雑状況を提供しない催事は「なし」を選びます。来場者向けの `saiji.html` には「情報なし」と表示され、`monitor.html` には場所だけが表示されます。この状態は15分以上経過しても「要確認」に変わりません。

| 状態 | 係が選ぶ目安 |
|---|---|
| 空いている | 待ちが少なく案内できる |
| やや混雑 | 少し待ちがある |
| 混雑 | 待ちが多い |
| 受付停止・終了 | 受付を止めている、または催事が終わった |
| なし | 混雑状況を提供しない |

具体的な待ち時間の基準は、運営側でそろえて係へ伝えてください。初期状態の「未更新」は登録直後の表示で、係の通常更新では選べません。

`saiji.html` の混雑表示は、最後の更新から15分以上たつと「要確認」になります。現行の **`monitor.html` は最後の状態を短く表示し、15分経過による「要確認」には切り替わりません**。モニターだけを見て更新の新しさを判断せず、係は定期更新を続けてください。

通信がない状態で混雑更新や催事公開はできません。過去に見た一部のページを表示できる場合はありますが、全ページの完全なオフライン動作を保証する仕組みではありません。通信障害時は会場案内や紙の資料で補います。

ホーム画面への追加は、iPhone では Safari の共有メニュー、Android では Chrome のメニューなどから行います。表示名や追加方法は端末により異なります。

## 10. 利用量・料金を確認する

設定・小規模な試験は Spark の無料枠で始められますが、**文化祭当日も無料枠に収まるとは限りません。** Firestore は閲覧時の読み取り、混雑情報の配信、再接続などでも利用量が増えます。

2026年9月27日の公式資料では、Firestore の無料枠は読み取り **1日50,000回**、書き込み **1日20,000回**、保存 **1 GiB** などです。無料枠の日次リセットは日本時間の午前0時ではなく、太平洋時間の午前0時ごろです。[公式：Firestore の料金・無料枠](https://firebase.google.com/docs/firestore/pricing)

このプログラムで、42件の公開催事と41件の混雑データがある催事一覧を初めて読むと、一覧の情報を含め概算で約84件分の読み取りが発生します。600回の新規読み込みなら約50,400件となる計算で、さらに変更配信・ほかのページの閲覧などが加わります。これは現在のプログラムからの概算で、実際の請求量や来場者数の上限を示すものではありません。

1. Firebase → Firestore Database → **使用状況（Usage）** で、試験前後の読み取り・書き込みを確認する。
2. 想定する来場者数、ページ移動、係の更新頻度、モニター台数を考えて本番の利用量を見積もる。
3. 無料枠を超えそうな場合は、顧問・費用管理者と料金プランを決める。Spark で上限に達すると、取得・更新ができなくなることがある。
4. 従量課金の **Blaze** を使う場合は学校で承認した請求先と予算通知を設定する。予算通知は課金を自動停止する上限ではない。
5. 当日も利用状況を確認し、費用・通信障害の連絡先を決めておく。

写真を含む催事データは転送量にも影響します。[公式：Firebase の料金プラン](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)

<a id="guide-11"></a>
## 11. バックアップ・復旧・引き継ぎ

### 11-1. バックアップを取る

大きな変更の前、公開直前、文化祭終了後に行います。

| 保存するもの | 方法 | 注意点 |
|---|---|---|
| サイトのファイル一式 | GitHub の Code → Download ZIP、または手元のフォルダを日付付きで複製 | GitHub 上にないローカル変更は ZIP に含まれない |
| 公開中の催事・写真 | [付録](#backup)で `events.json` と `map-local-data.js` を保存 | 管理画面にダウンロード・取り込みボタンはない |
| 公開中の Firestore ルール | Firebase のルール画面からコピーして日付付き保存 | フォルダのルールと本番のルールが同じか確認する |
| 係・管理者の設定 | UID・表示名・権限・担当・有効状態を、学校の非公開の引き継ぎ資料に記録 | 公開 GitHub や README に個人のログイン情報を載せない |
| Firebase・GitHub の運用情報 | 下の引き継ぎ台帳を非公開の場所で保管 | パスワード・復旧コードは別の安全な保管場所へ |

付録のファイルは**催事の予備データ**であり、混雑履歴・ユーザー・Authentication の完全なバックアップではありません。Firestore 全体のエクスポートが必要な場合は、公式のエクスポート／インポートを管理担当者が実施します。これは課金の有効化や Cloud Storage の保存先が必要で、Authentication のユーザーは別管理です。[公式：Firestore のエクスポートとインポート](https://firebase.google.com/docs/firestore/manage-data/export-import)

### 11-2. 間違えたときに戻す

- **HTML・画像・設定ファイルを間違えた場合：** 保管した同名ファイルを GitHub に再アップロードする。画像は `sw.js` のキャッシュ名も新しい値へ変える。Actions の成功後に表示を確認する。
- **公開催事を間違えた場合：** 管理画面で正しい内容へ直して再公開する。GitHub を戻すだけでは Firestore の公開催事は戻らない。
- **新しい空の Firebase に催事を再構築する場合：** 保存した `events.json` を公開先へ置き、新プロジェクトの設定・ルール・管理者を準備して[7章](#guide-7)から公開し直す。係のアカウントと担当も再登録する。
- **既存 Firebase の公開催事をまとめて復元する場合：** 現行の編集画面には JSON 取り込み機能がない。少数なら画面で直し、大量ならバックアップを持ってシステム担当者に復元を依頼する。初回状態に戻す目的で `siteContent/events` などを不用意に削除しない。
- **すべての管理者が入れなくなった場合：** Firebase コンソールへ入れる担当者が、Authentication のユーザーと `users/{UID}` を照合し、[5章](#guide-5)の管理者設定を復旧する。

### 11-3. 後任にアクセス権を渡す

1. **GitHub：** リポジトリの Settings → Collaborators または Collaborators and teams / Manage access から後任を招待し、後任が招待を承認する。ファイル更新に必要な権限を確認する。個人所有リポジトリでは共同編集者を追加しても所有者の権限をすべて渡せるわけではないため、卒業後も公開設定を管理できる所有体制を決める。
2. **Firebase：** 歯車 → プロジェクトの設定 → **ユーザーと権限（Users and permissions）** から、後任の Google アカウントを追加する。通常の設定・データ管理には編集者相当など必要な役割を選び、メンバー管理・請求管理はそれができる顧問等の責任者を残す。
3. **サイト：** 後任の Authentication アカウントを作り、サイト内 `admin` を付ける。
4. 後任自身のアカウントで、ファイル更新・Firebase の設定確認・サイトの催事公開ができることを確認する。
5. 確認後、卒業する係や不要になった管理者のサイト内権限を停止し、GitHub・Firebase の旧担当者の権限も責任者が整理する。管理できる人をゼロにしない。

個人のパスワードを次の人に渡して使い続けるのではなく、後任自身のアカウントへ権限を付けます。二段階認証を使っている管理アカウントは、卒業後の復旧方法も責任者が管理してください。

[公式：GitHub のアクセス管理](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-teams-and-people-with-access-to-your-repository) / [公式：Firebase プロジェクトのアクセス管理](https://firebase.google.com/docs/projects/iam/overview)

### 11-5. 文化祭が終わったら

1. 各催事を「受付停止・終了」にする。
2. 必要なバックアップを取り、係の更新権限を停止する。
3. 公開を続けるか終了するかを、顧問・運営で決める。
4. 公開終了する場合は GitHub の Settings → Pages の **Unpublish site** などから公開を停止する。翌年度の再公開設定も記録する。[公式：Pages の公開停止](https://docs.github.com/en/pages/getting-started-with-github-pages/unpublishing-a-github-pages-site)

現在の表紙には「宇工祭終了後の閲覧はできません」とありますが、**指定日時に自動で公開停止する処理はありません**。終了作業が必要です。また Pages を停止しても、公開リポジトリのファイルや Firestore の公開読み取り、すでに端末へ保存されたデータまで消えるわけではありません。資料の保存・非公開化・データ保持の扱いは、責任者がそれぞれ判断してください。

## 12. 困ったときの確認表

| 症状 | 確認・対処 |
|---|---|
| サイトが404になる | Settings → Pages のブランチと `/ (root)`、直下の `index.html`、Actions の公開結果、URL の大文字小文字を確認する |
| `main` が Pages で選べない | 先に README やファイルを保存してブランチを作る |
| Settings や Pages を操作できない | GitHub の権限と、学校 Organization の Pages 利用設定を所有者に確認する |
| ページは開くが管理画面が読み込めない | JS ファイルのアップロード漏れ、インターネット接続、学校のネットワークから Firebase への接続を確認する |
| メール・パスワードでログインできない | 同じ Firebase プロジェクトで Authentication を有効にしたか、ユーザーを追加したか、入力内容が正しいかを確認する |
| パスワードを忘れた | サイトに再設定ボタンはない。Firebase のユーザー管理で担当者がパスワード再設定の操作を行う |
| ログインできるが権限がない | `users` のドキュメント ID が UID と一致するか、`role` が `admin` または `staff` か、`active` が boolean の `true` か確認する |
| 係が `admin.html` に入れない | 管理者専用ページなので、係には `crowd-admin.html` を案内する |
| 担当催事が表示されない | サイトの権限設定で、その係に今年度の催事が割り当てられているか確認する |
| 催事が未登録で混雑を更新できない | 管理者が「未登録の催事を登録」を押す |
| 保存権限がない・`permission-denied` | Firestore のルールを公開したか、`siteContent/events` と `publishedEvents` のルールもあるか、対象ユーザーが有効か確認する |
| 初回用・予備データばかり表示される | 初回公開済みか、`projectId` と `(default)` データベースが正しいか、Firestore のルールと通信を確認する |
| 「別の担当者が先に更新しました」と出る | 未保存の変更を控えてから再読み込みし、最新データに必要な変更を加えて再公開する |
| 写真を公開できない | 写真を小さくするか、写真の追加を数件ずつに分ける |
| `events.json` を変えても催事が変わらない | 公開データは Firestore が優先される。催事編集画面で更新する |
| 地図から古い／別の催事が開く | `map-links.json` の ID と `publishedEvents` を照合する。予備の `map-local-data.js` も更新する |
| 古い画像・画面が残る | 公開完了を確認し、`sw.js` のキャッシュ名を更新して再公開する。端末で再読み込みし、タブを閉じて開き直す |
| 催事一覧やボタンが二重になる | `saiji.html` の末尾にもう一つの HTML を追記していないか確認し、正しいファイル全体で置き換える |
| 混雑の最新情報を取得できない | 通信、Firebase の利用上限、ルールを確認する。最新状態と決め付けず、会場で確認する |
| 新年度の編集が旧年度にも反映された | コピーしたサイトの `firebase-config.js` が旧プロジェクトを向いていないか確認し、影響した内容を管理者が戻す |

### Firestore のデータ

「コレクション」はデータの種類ごとの入れ物、「ドキュメント」はその中の1件です。

| 保存先 | 内容 | 作成する方法 |
|---|---|---|
| `users/{UID}` | 表示名、権限、有効状態、担当催事 ID | 最初の管理者はコンソール、その後はサイトの権限設定 |
| `siteContent/events` | 催事の分類・表示順、更新版の識別情報 | 催事編集画面で公開 |

| `crowd/{催事ID}` | 最新の混雑状況 | 未登録催事の登録、その後は状態ボタン |
| `crowdHistory/{変更ID}` | 混雑の更新者・日時・状態 | 混雑更新時に自動作成 |

ログイン用のメール・パスワードは Firestore の `users` ではなく、Authentication が管理します。

## 付録. 公開中の催事を予備ファイルとして保存する

公開中の催事は GitHub の ZIP に入りません。現行の編集画面に書き出しボタンがないため、ここだけはパソコンのブラウザの開発者ツールを使います。次の処理は公開データを読み、パソコンへ保存するリンクを作ります。Firebase への書き込みはしません。

1. ほかの担当者の催事編集をいったん止める。
2. パソコンの Chrome または Edge で、**対象年度の公開サイトの `index.html`** を開く。GitHub のファイル一覧画面では実行しない。
3. 右上メニュー → その他のツール → デベロッパーツールを開き、**Console** を選ぶ。
4. 下のコードを確認して実行する。貼り付けがブラウザに制限される場合は、内容を理解できるシステム担当者に作業を依頼する。
5. ページ上部に出る2つの保存リンクをそれぞれ押す。`events.json` と `map-local-data.js` が保存される。
6. 保存した `events.json` をテキストエディターで開き、最新の催事名になっていることを確認する。
7. 日付付きのバックアップフォルダへ保管する。予備データを更新する場合は、作業フォルダの同名ファイルもこの2つで置き換えて GitHub にアップロードする。
8. 同名ファイルがあって `events (1).json` などになった場合は、アップロード前に元のファイル名に戻す。

```js
(async () => {
  const {loadEventsData} = await import("./event-data.js");
  const result = await loadEventsData();
  if (result.source !== "firestore" || result.warning) {
    throw new Error("公開データを取得できません。通信と Firebase の設定を確認してください。");
  }
  const readJson = async (file) => {
    const response = await fetch(file, {cache: "no-store"});
    if (!response.ok) throw new Error(`${file} を取得できませんでした。`);
    return response.json();
  };
  const links = await readJson("map-links.json");
  const positions = await readJson("map-positions.json");
  const box = document.createElement("div");
  box.style.cssText = "padding:20px;background:white;color:black;position:relative;z-index:99999";
  box.textContent = "最新の催事を取得しました。次の2ファイルを保存してください： ";
  const addDownload = (name, text, type) => {
    const a = document.createElement("a");
    a.href = URL.createObjectURL(new Blob([text], {type}));
    a.download = name;
    a.textContent = `${name} を保存`;
    a.style.cssText = "display:block;padding:12px;color:blue;text-decoration:underline";
    box.append(a);
  };
  addDownload("events.json", JSON.stringify(result.data, null, 2) + "\n", "application/json");
  addDownload(
    "map-local-data.js",
    "// 公開中の催事と地図から保存した予備データ。\nwindow.MAP_LOCAL_DATA = " +
      JSON.stringify({events: result.data, links, positions}) + ";\n",
    "text/javascript"
  );
  document.body.prepend(box);
})();
```

この処理は地図との対応を自動修正しません。新しい催事の地図 ID 対応は、先に[8-3](#guide-8)の手順で更新してください。作成したリンクはページを再読み込みすると消えます。
